# 宣伝室（Promo Room）計画書 — Opus 5 引き継ぎ用

作成: 2026-07-26（Fable 5セッションでよこぼ承認済みの方針を文書化）
実装対象リポ: `20260428_webサイト刷新`（本番 https://yokobo-ai-lab.vercel.app/ ）

## 1. 背景とゴール

よこぼ（非エンジニア・スマホ運用）が「気が向いたときに」サイト全体の宣伝をXに投稿したい。
現状はadmin画面の記事ごとのXボタンしかなく、**画像付き投稿ができない**。

ゴール:
- スマホから、**サイト内のwebp画像を添付した宣伝投稿**が数タップで作れる
- 記事単位だけでなく「サイト全体の宣伝」「ランダムに過去実験を発掘」ができる
- 宣伝文はAIラボ側（Claude/Codexセッション）がストックを補充する形で連結する

## 2. 確定済みの方針（2026-07-26 よこぼ承認）

- **X APIは使わない**。developer登録・キー管理・無料枠制限を避ける
- 代わりに **Web Share API（`navigator.share({ files, text })`）** を使う。
  スマホの共有メニュー→Xアプリ→画像添付済み・文章入力済みの投稿画面が開き、
  最後の投稿ボタンはよこぼが押す（誤爆・自動投稿リスクなし）
- 進め方は **試作→よこぼのスマホで動作確認→本実装** の順
- 画像は断定で1枚選ばず **候補3〜4枚を提示してよこぼが選ぶ**
  （メディア台帳計画で決めた全セッション共通ルール。`_LAB_HQ` 参照）

## 4. 設計

### 画面: `/admin/promo`（モバイルファースト）

adminと同じパスワード認証。4ステップの縦一列UI（スマホ親指操作前提）。

1. **ネタ選択**: 「サイト全体」「最新記事」「ランダム実験発掘」「記事を選ぶ」のボタン
2. **画像選択**: ネタに応じた候補webpを3〜4枚グリッド表示、タップで1〜4枚選択。
   「別の候補」ボタンで引き直し
3. **文章選択**: テンプレ数種＋宣伝文ストック（後述）から選択、その場で編集も可
4. **シェア**: `navigator.share({ files, text })` を実行。
   - 事前に `navigator.canShare({ files })` でチェック
   - 使えない環境（PC等）では「文章をコピー＋画像をダウンロード」に自動フォールバック

### 画像一覧の取得

Vercel本番のserverless環境で `public/` をfs列挙するのは不確実なので、
**ビルド時にマニフェストを生成する**方式にする:
- `scripts/gen-image-manifest.mjs` が `public/**/*.webp` を走査して
  `data/promo-images.json`（パス・フォルダ分類・ファイルサイズ）を出力
- `package.json` の build に前段として組み込む
- admin画面から画像をアップロードした場合はGitHubコミット→再デプロイで反映される
  （即時反映は求めない。フェーズ1では割り切る）

### 宣伝文ストック（AIラボ連結の要）

- `data/promo-drafts.json`: `{ id, kind: "site"|"article"|"random", text, usedAt|null }` の配列
- AIラボ側のセッション（Claude/Codex）がこのJSONに新しい宣伝文を補充してコミットする。
  補充手順は本ドキュメントと `AGENTS.md` の慣例に従い、Codexでも書ける単純なJSON編集にする
- 使用済みは `usedAt` を記録（使ったかどうかはシェア実行時にAPIでマーク。
  GitHub保存の仕組みは `github_storage_guide.md` と同じ経路を使う）

### webpがXアプリに渡らなかった場合の保険

share sheet経由の挙動は機種・Xアプリのバージョン差がある。試作で確認すべき順:
1. webpのまま `files` に渡す（第一候補）
2. ダメなら Canvas でクライアント側 jpeg 変換してから渡す
3. `files` 自体が渡らないなら「画像は端末に保存＋文章は自動コピー→Xアプリで手動添付」に切替

### フェーズ1.5: 画像の選別とプリセット — 完了（2026-07-27）

よこぼからの指摘:「サイト全体の宣伝で出る画像がほぼ使えない。一度も使ってない画像や、
開発途中で上がった画像が混ざっていてゴミ」

調べた結果:
- 当時の候補75枚のうち、サイトのどこからも参照されていないのは15枚だけだった。
  つまり問題は「未使用」ではなく**絵として宣伝に耐えないもの**が混ざっていたこと
- 75枚すべてを実際に見て確認したところ、原因は4種類:
  日付が焼き込まれた古いサムネイル、ロゴやLPの案出し資料、開発中のスクリーンショット、
  背景・枠・アイコンなどの画面部品

対応:
- **`data/promo-curation.json` を新設**。実物を見て選んだ結果を持つファイルで、
  ここにあるものだけが候補になる。外したものは理由つきで `rejected` に残してあるので、
  同じ画像を何度も見直さずに済む
- 選別は**AIが実物を見てやる**。よこぼが手でラベル付けする運用にはしない
  （所長は「開かない・撮らない」前提。`_LAB_HQ/LAB_CHARTER.md`）
- 生成スクリプトは未選別の画像を一覧で警告する。新しい絵が増えても黙って候補に混ざらない
- 結果: 106枚中49枚が候補。タグ（キャラクター/ラボの世界/遊べるもの/実験の記録/歴代サイト/看板）で絞り込める
- **サイトの画像は消していない。** 候補75枚のうち60枚は現に使われているため、
  整理と称して消すとページが壊れる。宣伝に使うかどうかと、サイトに要るかどうかは別問題

プリセット（`data/promo-presets.json` + `/api/promo-presets`）:
- ネタ・画像・文章の組み合わせに名前を付けて保存し、1タップで呼び戻せる
- 端末ではなくサーバー側に置く。スマホとPCで同じものが見えるように
- 同じ名前で保存し直すと上書き。最大30件

### フェーズ1.6: リンクをリプ欄に回す — 完了（2026-07-27）

本文に外部リンクを入れるとリーチが落ちる、という話への対応。
複数の解説記事で「本文のリンクは初速が3〜5割落ちる」「最初のリプに置くのが定石」と
一致していた（ただし出典はマーケティング系ブログで、X公式の仕様ではない）。

**自動でリプまで投稿することはできない。** まだ存在しない投稿には返信をぶら下げられず、
それをやるにはX APIが要る（不採用の理由は5節のとおり）。そこで2タップに分けた:

- 既定は「リンクはリプ欄に」。本文からURLを外して共有する
- 投稿後に「② リンクをコピー」を押すと、URLがクリップボードに入る。
  自分の投稿に返信して貼る
- 「本文に入れる」に切り替えれば1タップで従来どおり
- 選んだほうは localStorage（`promo-link-in-reply`）に残る
- 文字数の表示もモードに合わせて変わる（リプ運用ならURLの23文字を数えない）
- クリップボードが使えない端末では、リンクを枠に出して手でコピーできる

### フェーズ1.8: 文章テンプレを「告知型」から作り直し — 完了（2026-07-28）

外部（Grok）に @yokobo_ai のインプが伸びない理由を分析させたところ、
リンク位置とビジュアルの指摘は1.6・1.7で対応済みだった一方、
**文章テンプレが全部「報告型」**である点だけが未対応で残っていた。
実際、既定の1番目が `【新記事】{タイトル}` で、分析が「悪い例」として挙げた形そのものだった。

`buildTemplates()` を型つきに変え、ネタごとに上から並べた:

| 型 | ねらい |
|---|---|
| フック | 1行目で結果や意外性を言う。告知型は素通りされやすいため |
| 質問 | 返信を誘って終わる。返信はいいねより重いシグナルとされる |
| 報告 | 従来の告知型。落ち着いて出したいときのために残す |

- STEP 3に一行の説明を出して、どちらを選ぶと伸びやすいと言われているかを画面上で分かるようにした
- テンプレのボタンには型のラベルを付けた（`.promoTemplateLabel`）
- 文章はこれまでどおり枠の中で自由に直せる。テンプレはあくまで出発点
- 根拠はマーケティング系の解説であり**X公式の仕様ではない**（1.6と同じ扱い）。
  だから報告型を消さず、選べるままにしてある

同じ分析から出た残りの案（未着手、やるなら別途）:
- **動画の共有**: `navigator.share` は mp4 も渡せるが、宣伝室は今のところ画像のみ。
  過去に伸びたのは3Dゲームの動画で、素材はラボの各パイプラインに揃っている
- **投稿ログ**: 何をいつどの型で宣伝したかを自動で残す。フェーズ2の投稿履歴と同じ話。
  型を分けた効果を後から言えるようにするなら、これが要る
- 1日8〜15件のリプライ・投稿直後の反応対応は人の運用で、宣伝室の守備範囲外

### フェーズ2の下見: 動画の共有（実機テスト待ち）

動画をGitHubに置くと容量を食うため、**外部（Cloudflare R2を想定）に置いてURLから読む**方式にする。
`navigator.share` に渡すのはFileなので、置き場所は取得できればどこでもよい。

`/experiments/share-test` に動画の枠を追加（フェーズ0と同じ作り）:
- URLを入れて「動画を用意する」→ fetchしてFile化。URLは端末に記憶（`share-test-video-url`）。
  `?video=<URL>` でも渡せる
- **方式V** = 動画をそのまま共有 / **方式W** = 端末に保存して手で添付（保険）
- 取得失敗時はCORS設定を疑うようメッセージに出している

PCで確認済み: URLの記憶・fetch・File化（7.3MB表示）・方式Wの有効化・
共有非対応端末での方式V無効化。**残りは実機で1回タップするだけ。**

容量の見込み（実測。`20260702_CM動画作成パイプライン/out`）:

| 作り直しの強さ | 15秒CMのサイズ |
|---|---|
| 現状のまま | 16.4MB（1080×1920 / 30fps / 8.5Mbps） |
| CRF 21 | 9.8MB |
| **CRF 23（採用予定）** | **7.3MB**（4.1Mbps） |
| CRF 26 | 4.7MB |

Xは投稿時にどのみち再圧縮するので、CRF 23で出し直せば見た目を保ったまま半分以下になる。
テスト用の1本は `20260702_CM動画作成パイプライン/out/share-test/cm-15s-crf23.mp4` に用意済み。

**R2の置き場所（2026-07-28に用意）**:

| 項目 | 値 |
|---|---|
| バケット | `yokobo-lab-media` |
| 公開URL | `https://pub-b41150828c6b4ba281393f859abc6865.r2.dev` |
| テスト動画 | `/promo/cm-15s-crf23.mp4`（7.3MB） |
| CORS許可元 | `https://yokobo-ai-lab.vercel.app` と `http://localhost:3000`（GET/HEAD） |

つまずいた点:
- R2はアカウントで**一度ダッシュボードから有効化**しないとAPIが `10042` で断る。よこぼ本人の操作
- `wrangler login` の待ち時間は**120秒**。ブラウザで許可を押すのが遅れると時間切れになる（2回失敗した）
- `wrangler r2 bucket cors set` のJSONは `{"rules":[...]}` の形。S3形式（配列直書き）は受け付けない
- CORS設定の反映に十数秒かかる。直後のfetchは `Failed to fetch` になるので、慌てて設定を疑わない
- アップロードは `--remote` を必ず付ける（付けないとローカル模擬ストレージに書いて成功表示のまま本番404）
- put後は `r2 object get` で読み戻してサイズ照合した（7,654,972バイト一致）

**実機テスト結果（2026-07-28）: 方式Vで動画が渡った。** そのまま共有する方式を採用する。

- 動画は選んだ時点でR2から取ってFileにする（共有ボタンを押してから読むとiOSで弾かれるため。画像と同じ理由）
- 読み込み中は共有ボタンが「動画を準備中…」になる
- 共有が使えない端末では、動画を端末に保存して手で添付する形に落ちる
- 候補札にはポスター画像（動画から1コマ抜いたjpg・120KB）と長さ・サイズを出す
- プリセットは画像だけを覚える（動画は入れていない）

動画を増やす手順:
1. `ffmpeg -i 元.mp4 -c:v libx264 -crf 23 -preset slow -pix_fmt yuv420p -c:a aac -b:a 128k -movflags +faststart 出力.mp4`
2. ポスター: `ffmpeg -ss 1.5 -i 出力.mp4 -frames:v 1 -vf scale=540:-2 -q:v 4 出力.jpg`
3. `wrangler r2 object put yokobo-lab-media/promo/<名前>.mp4 --file ... --content-type video/mp4 --remote`（jpgも同様）
4. `public/promo-videos.json` に1件足してデプロイ

## 6. 制約・ルール（引き継ぎ先へ）
